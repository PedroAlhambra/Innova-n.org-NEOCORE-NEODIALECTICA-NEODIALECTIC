# ES · Castellano

## 1. Principio de fuente y proyección

La **fuente de autoridad intelectual y genealógica no es GitHub ni ninguna plataforma de publicación**.

La fuente es **Innova_N**, bajo dirección humana de **Pedro Martínez Alhambra · Neo0™**, dentro del sistema vivo **NEOCore™ / Neodialectica Framework™ / Network**.

GitHub funciona como **primera proyección WEB4™ pública, versionada y trazable**. Cualquier copia en Substack, WordPress, Ghost, GitLab, Codeberg, Medium, Hashnode, DEV, repositorios académicos, archivos web u otras plataformas debe declararse como **proyección, espejo o sindicación** de contenido originado y versionado en el sistema.

Ninguna plataforma receptora adquiere por la mera copia condición de fuente primaria, autoría, origen conceptual o autoridad canónica.

## 2. Objetivos

La proyección distribuida persigue cinco funciones simultáneas:

1. **redundancia documental** frente a desaparición, cierre o dependencia de una sola plataforma;
2. **trazabilidad temporal y genealógica** mediante commits, fechas, hashes, releases, identificadores persistentes y archivos de terceros;
3. **descubrimiento** en buscadores, redes de lectura, comunidades técnicas, académicas y culturales;
4. **contexto contra la apropiación o reducción**, haciendo visible la cronología y las relaciones entre conceptos;
5. **expansión de la Síntesis Abierta**, conduciendo a lectores de cada plataforma hacia la fuente documental, los manifiestos relacionados y sus espacios de contraste.

## 3. Regla de sindicación

No se busca producir spam ni copias descontroladas. Se construye una **red de proyecciones coherentes y enlazadas**.

Cada proyección debe conservar, como mínimo:

- título y numeración canónica del manifiesto;
- autoría y procedencia;
- fecha de versión y, cuando sea posible, SHA o identificador de la versión fuente;
- enlace al manifiesto canónico en la proyección WEB4™ inicial;
- enlace al índice general de manifiestos;
- enlace a su Síntesis Abierta cuando exista;
- aviso de que la plataforma receptora es una proyección y no la fuente originaria;
- licencia y condiciones de reutilización aplicables;
- enlaces recíprocos entre proyecciones cuando aporten valor real al lector.

## 5. Pie mínimo de navegación

> **Continuidad documental**  
> Manifiesto canónico · Índice de manifiestos · Síntesis Abierta · Neodialectica Framework™ / Network · otras proyecciones verificadas.

## 6. Jerarquía de proyecciones

### Nivel A · Fuente documental versionada

- NEOCore™ como sistema vivo de origen y relación;
- repositorio público Innova_N en GitHub como proyección WEB4™ inicial;
- releases y commits como traza técnica pública.

### Nivel B · Espejos Git completos

Repositorios secundarios deben preservar historial, ramas relevantes, tags y commits siempre que la plataforma lo permita. Se priorizan GitLab, Codeberg/Gitea y otros forges compatibles.

### Nivel C · Publicación legible y descubrimiento

Substack, WordPress, Ghost y plataformas equivalentes pueden publicar cada manifiesto como artículo navegable. La publicación debe conservar procedencia y enlace canónico.

### Nivel D · Comunidades especializadas

Hashnode y DEV pueden proyectar especialmente los manifiestos y análisis con dimensión tecnológica, IA, gobernanza, trazabilidad, WEB4™, NEOCore™ y arquitectura humano–IA.

### Nivel E · Archivo independiente y prueba temporal

Se recomienda depositar hitos o releases significativos en sistemas persistentes de archivo e identificación, por ejemplo Zenodo/DOI, Software Heritage y otros archivos públicos adecuados. Su función no es sustituir el origen, sino crear evidencia independiente de existencia, versión y fecha.

## 7. Regla SEO y de descubrimiento

La expansión no debe competir consigo misma innecesariamente. Cuando la plataforma admita URL canónica o importación con procedencia, debe señalarse la versión elegida como referencia. Cuando no lo permita, cada copia conservará una cabecera visible de procedencia y enlaces hacia el nodo canónico.

Las introducciones pueden adaptarse al público de cada plataforma, pero el cuerpo canónico del manifiesto no debe alterarse silenciosamente. Toda modificación sustantiva requiere nuevo estado/versionado en la fuente y posterior resincronización.

## 8. Política de actualización

```text
NEOCore™ / dirección humana
        ↓
versión pública validada
        ↓
GitHub · WEB4™ inicial · commit / SHA / release
        ↓
manifiesto de proyección
        ↓
espejos Git + publicaciones + archivos persistentes
        ↓
verificación de enlaces y versión
        ↓
registro de proyecciones activas
```

Las proyecciones son **downstream**. No se debe editar una copia secundaria y dejarla divergir sin retornar el delta a la fuente.

## 9. Registro de proyecciones

Cada destino debe registrarse con:

| Campo | Contenido |
|---|---|
| Plataforma | nombre del destino |
| URL | URL pública |
| Tipo | espejo Git / artículo / archivo / índice |
| Contenido | manifiestos o subconjunto publicado |
| Versión fuente | SHA, tag o release |
| Fecha de sincronización | fecha UTC |
| Método | manual / API / RSS / importación / mirror |
| Estado | activo / pendiente / desincronizado / archivado |

## 10. Límite operativo

La expansión debe aumentar **comprensión, verificabilidad y acceso**, no volumen ciego. No se usarán automatismos para evadir políticas de plataformas, generar cuentas falsas, manipular métricas ni acosar comunidades. La fuerza de la red debe proceder de la multiplicación de fuentes verificables, del valor del contenido y de su capacidad de abrir contraste.

## 11. Estrategia de Comentario Contextual Enlazado™

La siguiente capa de proyección no necesita depender de publicar continuamente piezas nuevas desde cero. Cuando una conversación pública, noticia, publicación profesional, debate técnico o intervención institucional toque de forma material una cuestión ya trabajada por Innova_N, puede intervenirse **desde Innova_N mediante un comentario breve, contextual y directamente enlazado al nodo canónico más específico**.

La regla es:

```text
HECHO / PUBLICACIÓN / DEBATE EXTERNO
        ↓
RELACIÓN REAL CON EL MARCO
        ↓
COMENTARIO BREVE DE INNOVA_N
        ↓
UNA IDEA O DELTA PERTINENTE
        ↓
ENLACE AL NODO CANÓNICO MÁS ESPECÍFICO
        ↓
MANIFIESTO / ANÁLISIS / AUDITORÍA / SÍNTESIS ABIERTA
        ↓
POSIBLE CONTRASTE Y RETORNO AL MARCO
```

No se enlazará por defecto a la portada del repositorio cuando exista una pieza más precisa. Se prioriza:

1. el manifiesto directamente relacionado;
2. el análisis o auditoría concreta cuando el comentario se refiera a un caso;
3. la Síntesis Abierta correspondiente cuando el objetivo principal sea provocar debate;
4. el índice general sólo cuando el objeto sea realmente el marco completo.

El comentario debe **aportar contexto antes del enlace**. No debe consistir en dejar una URL desnuda ni en repetir el mismo mensaje indiscriminadamente.

### Principio de Proyección por Pertinencia™

> **Innova_N no entra en conversaciones públicas para ocupar espacio. Entra cuando existe una relación material con trabajo ya trazado o cuando el nuevo caso puede producir un delta. Cada intervención debe poder devolver al lector a la fuente exacta que permite comprender, contrastar o ampliar esa relación.**

Esta estrategia convierte redes como LinkedIn en **capa de descubrimiento y entrada**, no en fuente canónica. El contenido sustantivo permanece versionado y trazable; el comentario actúa como puente contextual hacia él.

Cuando el debate externo produzca una objeción, fuente, contraejemplo o mejora material, se devolverá al repositorio mediante la Síntesis Abierta correspondiente, conservando genealogía y trazabilidad.

# EN · English

## 1. Source and projection principle

The **intellectual and genealogical authority does not originate in GitHub or in any publishing platform**.

The source is **Innova_N**, under the human direction of **Pedro Martínez Alhambra · Neo0™**, within the living **NEOCore™ / Neodialectica Framework™ / Network** system.

GitHub operates as the **first public, versioned and traceable WEB4™ projection**. Any copy published on Substack, WordPress, Ghost, GitLab, Codeberg, Medium, Hashnode, DEV, academic repositories, web archives or other platforms must be identified as a **projection, mirror or syndication** of content originated and versioned in the system.

No receiving platform becomes the primary source, conceptual origin, author or canonical authority merely by hosting a copy.

## 2. Objectives

Distributed projection serves five simultaneous functions:

1. **documentary redundancy** against disappearance, closure or dependence on a single platform;
2. **temporal and genealogical traceability** through commits, dates, hashes, releases, persistent identifiers and third-party archives;
3. **discovery** across search engines and technical, academic, cultural and reading communities;
4. **context against appropriation or reduction**, making chronology and conceptual relationships visible;
5. **expansion of Open Synthesis**, directing readers from each platform to the documentary source, related manifestos and spaces for contrast.

## 3. Syndication rule

The objective is not uncontrolled duplication or spam. It is a **coherent, interlinked projection network**.

Every projection should preserve at least:

- canonical title and manifesto number;
- authorship and provenance;
- version date and, where possible, source SHA or version identifier;
- link to the canonical manifesto in the initial WEB4™ projection;
- link to the complete manifesto index;
- link to its Open Synthesis where available;
- notice that the receiving platform is a projection rather than the originating source;
- applicable licence and reuse conditions;
- reciprocal links between projections where they provide genuine reader value.

## 4. Minimum provenance header

> **NEODIALECTICAL PROJECTION™ · DISTRIBUTED COPY**  
> Intellectual and genealogical source: **Innova_N · NEOCore™ / Neodialectica Framework™ / Network**.  
> Human direction and origin: **Pedro Martínez Alhambra · Neo0™**.  
> This page is a public projection of the system; the hosting platform is not the originating source and acquires no authorship by hosting it.  
> Canonical version and traceability: **[source-version URL / SHA / release]**.

## 5. Minimum navigation footer

> Canonical manifesto · Manifesto index · Open Synthesis · Neodialectica Framework™ / Network · other verified projections.

## 6. Projection hierarchy

### Level A · Versioned documentary source

- NEOCore™ as the living system of origin and relation;
- the public Innova_N GitHub repository as the initial WEB4™ projection;
- releases and commits as public technical trace.

### Level B · Complete Git mirrors

Secondary repositories should preserve history, relevant branches, tags and commits whenever the destination supports them. GitLab, Codeberg/Gitea and other compatible forges are preferred.

### Level C · Readable publication and discovery

Substack, WordPress, Ghost and equivalent platforms can publish each manifesto as a navigable article. Provenance and canonical links must remain visible.

### Level D · Specialist communities

Hashnode and DEV can particularly project manifestos and analyses concerning technology, AI, governance, traceability, WEB4™, NEOCore™ and human–AI architecture.

### Level E · Independent archive and temporal evidence

Significant milestones or releases should be deposited in persistent archival and identification systems such as Zenodo/DOI, Software Heritage and other appropriate public archives. Their function is not to replace origin, but to create independent evidence of existence, version and date.

## 7. SEO and discovery rule

Expansion should not needlessly compete with itself. Where a platform supports canonical URLs or provenance-aware imports, the chosen reference version should be identified. Where this is unavailable, each copy should preserve a visible provenance header and links to the canonical node.

Introductions may be adapted for each platform's audience, but the canonical manifesto body must not be silently altered. Any substantive change requires a new source version followed by re-synchronisation.

## 10. Operational limit

Expansion must increase **understanding, verifiability and access**, not blind volume. Automation must not be used to evade platform rules, create fake accounts, manipulate metrics or harass communities. The network gains strength from multiple verifiable projections, valuable content and its capacity to open genuine contrast.

## 11. Contextual Linked Comment Strategy™

The next projection layer does not need to depend on constantly publishing new standalone pieces. When a public conversation, news item, professional post, technical debate or institutional intervention materially touches a question already developed by Innova_N, Innova_N may intervene through a **brief contextual comment directly linked to the most specific canonical node**.

The rule is:

```text
EXTERNAL EVENT / POST / DEBATE
        ↓
REAL RELATION TO THE FRAMEWORK
        ↓
BRIEF INNOVA_N COMMENT
        ↓
ONE RELEVANT IDEA OR DELTA
        ↓
LINK TO THE MOST SPECIFIC CANONICAL NODE
        ↓
MANIFESTO / ANALYSIS / AUDIT / OPEN SYNTHESIS
        ↓
POSSIBLE CONTRAST AND RETURN TO THE FRAMEWORK
```

The repository homepage should not be the default destination when a more precise piece exists. Priority is given to:

1. the directly related manifesto;
2. the concrete analysis or audit when the comment refers to a case;
3. the corresponding Open Synthesis when the main objective is to provoke debate;
4. the general index only when the object is genuinely the framework as a whole.

The comment must **provide context before the link**. It should not consist of a bare URL or an indiscriminately repeated message.

### Principle of Projection by Relevance™

> **Innova_N does not enter public conversations merely to occupy space. It enters where a material relation exists with already traceable work or where a new case can produce a delta. Each intervention should return the reader to the exact source needed to understand, challenge or extend that relation.**

This turns networks such as LinkedIn into a **discovery and entry layer**, not a canonical source. Substantive content remains versioned and traceable; the comment acts as a contextual bridge to it.

Where external debate produces a material objection, source, counterexample or improvement, that contribution should return to the repository through the corresponding Open Synthesis, preserving genealogy and traceability.
