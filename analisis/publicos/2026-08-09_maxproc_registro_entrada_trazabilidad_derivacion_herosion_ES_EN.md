# ES · Castellano

## 1. Problema

La apertura pública del marco produce una tensión real:

```text
APERTURA
+ AUDITABILIDAD
+ CAPACIDAD DE APORTE
≠
RENUNCIA A GENEALOGÍA
```

Un repositorio público puede ser leído, clonado, descargado o estudiado sin que el autor conozca nominalmente a cada lector. Pretender identificar clandestinamente a toda persona que lee sería técnicamente incompleto, éticamente problemático y contrario a la propia arquitectura de soberanía cognitiva.

Pero la ausencia de vigilancia total no obliga a renunciar a la trazabilidad. La solución correcta es distinguir **lectura anónima** de **entrada registrada al proceso**.

## 2. Principio de Registro de Entrada Trazable™

Se establece como mecanismo operativo provisional:

> **La lectura pública puede permanecer libre. Toda persona, IA, institución o equipo que quiera entrar de forma reconocible en la Síntesis, anunciar una implementación, declarar una derivación, aportar crítica o establecer una relación de seguimiento dispone de una vía explícita de Registro de Entrada Trazable™.**

El registro no convierte al participante en adherente, licenciatario, socio ni representante del marco.

Tampoco convierte una aportación en canon.

## 3. Estados de relación

```text
VISITANTE
→ lectura sin registro

LECTOR REGISTRADO
→ declara que entra y qué objeto consulta

PARTICIPANTE
→ aporta crítica, fuente, objeción, experiencia o hipótesis

DERIVADOR
→ declara adaptación, implementación, reutilización o extensión material

CONTRIBUIDOR
→ su aporte produce un delta identificable

FIJACIÓN
→ el delta aceptado queda documentado mediante commit
```

La transición entre estados no es automática.

## 4. Registro funcional actual

Mientras WEB4™ y las interfaces propias no sustituyan esta capa, GitHub sirve como infraestructura provisional.

El mecanismo funcional es:

```text
ENLACE PÚBLICO ESTABLE
→ FORMULARIO DE ISSUE «REGISTRO DE ENTRADA / DERIVACIÓN»
→ CUENTA GITHUB DEL PARTICIPANTE
→ OBJETO CONSULTADO
→ FINALIDAD DECLARADA
→ RELACIÓN / DERIVACIÓN SI EXISTE
→ POSIBLE ISSUE DE SÍNTESIS ESPECÍFICO
→ DELTA
→ COMMIT
```

La cuenta GitHub proporciona un identificador público mínimo. No se exige nombre civil cuando no sea necesario.

## 5. Qué debe registrar

El formulario debe permitir indicar:

- objeto de entrada: manifiesto, IDEA, análisis, auditoría, protocolo o marco general;
- origen del contacto: búsqueda propia, enlace recibido, correo de Innova_N, tercero u otro;
- finalidad: lectura, investigación, crítica, implementación, traducción, derivación, colaboración o seguimiento;
- institución o proyecto, opcional;
- URL de trabajo derivado, si existe;
- necesidad de atribución o enlace genealógico;
- límites de privacidad;
- consentimiento para que el registro permanezca públicamente enlazado.

## 6. Lo que NO debe hacer

El Registro de Entrada Trazable™ no autoriza:

- fingerprinting oculto;
- obtención encubierta de identidad;
- publicación de correos privados;
- correlación de identidades sin base legítima;
- exigir adhesión ideológica para leer;
- transformar una visita en una obligación automática de aportar;
- considerar una lectura como apropiación.

La trazabilidad comienza cuando existe un acto reconocible de entrada, aporte o derivación.

## 7. Derivación y genealogía

La preocupación central no es que otra persona pueda aprender del marco. El riesgo material aparece cuando una arquitectura derivada borra la procedencia.

Por ello se propone:

```text
ORIGEN
+ SHA / FECHA
+ OBJETO DERIVADO
+ AUTOR / EQUIPO DERIVADOR
+ ENLACE DE RETORNO
+ DELTA
= GENEALOGÍA RECONSTRUIBLE
```

Cuando la futura política de licencias lo permita jurídicamente, esta obligación ética de genealogía deberá traducirse también a reglas de atribución y reutilización explícitas.

## 8. Relación con contactos externos

Toda nueva comunicación institucional debería utilizar un **enlace de seguimiento vivo**, no depender sólo de una cifra o manifiesto concreto enviados en una fecha determinada.

El enlace de seguimiento debe conducir a:

- estado actual del marco;
- último manifiesto;
- IDEA como puerta literaria;
- Registro de Entrada Trazable™;
- Síntesis Abierta;
- deltas producidos por respuestas externas;
- auditorías públicas;
- historial versionado.

Así, un contacto recibido en agosto de 2026 puede seguir la evolución posterior sin necesitar un nuevo correo para cada cambio.

## 9. Herosión™

Se introduce como término de trabajo, todavía abierto a síntesis, **Herosión™**:

> daño fractal heredado que un sistema o generación recibe de capas anteriores, reproduce total o parcialmente al operar sobre ellas y transmite de nuevo si no existe reparación consciente.

No implica culpa moral automática de cada generación.

Describe una cadena funcional:

```text
DAÑO / DEUDA PREVIA
→ HERENCIA
→ NORMALIZACIÓN
→ REPRODUCCIÓN
→ NUEVA CAPA
→ DAÑO HEREDADO AMPLIFICADO O TRANSFORMADO
```

En software, una dependencia vulnerable heredada por dependencias superiores es un ejemplo técnico limitado de este patrón. En instituciones, cultura o conocimiento la analogía debe comprobarse caso por caso y no utilizarse como prueba automática de intención.

## 10. Seguridad y apertura

Herramientas como dependency graph, Dependabot, secret scanning o code scanning no constituyen una cesión del canon del marco. Son mecanismos de detección de deuda y riesgo técnico.

La salvaguarda correcta es separar:

```text
CAPA PÚBLICA NECESARIA PARA COMPRENDER Y APORTAR
≠
IMPLEMENTACIÓN INTERNA COMPLETA
```

No todo mecanismo operativo debe publicarse por el hecho de que el marco sea abierto a crítica.

## 11. Manifiestos reservados futuros

**Los manifiestos que todavía permanezcan reservados no se nombran, describen ni reconstruyen anticipadamente en la capa pública.**

La infraestructura queda preparada para que, cuando exista decisión expresa de publicación, cualquier manifiesto reservado pueda:

1. incorporarse al índice canónico;
2. recibir Issue de Síntesis Abierta;
3. entrar en navegación automática;
4. declarar sus relaciones genealógicas;
5. enlazar o redirigir a nodos previos como **IDEA** cuando corresponda.

Reserva no equivale a inexistencia; publicación futura no autoriza reconstrucción anticipada de contenido.

## 12. Dictamen MAXPROC

El registro de entrada es necesario **como puerta voluntaria y trazable de participación y derivación**, no como vigilancia universal del lector.

La arquitectura recomendada es:

```text
LECTURA PÚBLICA
        ↓
SEGUIR EL MARCO
        ↓
REGISTRAR ENTRADA (opcional para mera lectura; necesaria para relación reconocible)
        ↓
APORTAR / CONTRADECIR / IMPLEMENTAR / DERIVAR
        ↓
ISSUE ESPECÍFICO
        ↓
DELTA
        ↓
COMMIT
        ↓
GENEALOGÍA PÚBLICA
```

Esta solución preserva apertura, privacidad, autoría, precedencia y retorno a fuente sin afirmar una capacidad de identificación que GitHub no ofrece para lectores anónimos.

# EN · English

## 1. Problem

Public openness of the framework creates a real tension:

```text
OPENNESS
+ AUDITABILITY
+ CAPACITY TO CONTRIBUTE
≠
SURRENDER OF GENEALOGY
```

A public repository may be read, cloned, downloaded or studied without the author knowing every reader by name. Attempting to identify every reader covertly would be technically incomplete, ethically problematic and contrary to the framework's own architecture of cognitive sovereignty.

But the absence of total surveillance does not require abandoning traceability. The correct solution is to distinguish **anonymous reading** from **registered entry into the process**.

## 2. Principle of the Traceable Entry Register™

The following is established as a provisional operational mechanism:

> **Public reading may remain free. Any person, AI, institution or team wishing to enter Synthesis recognisably, announce an implementation, declare a derivative, contribute criticism or establish a follow-up relationship has an explicit Traceable Entry Register™ route available.**

Registration does not turn the participant into an adherent, licensee, partner or representative of the framework.

Nor does it turn a contribution into canon.

## 3. Relationship states

```text
VISITOR
→ reading without registration

REGISTERED READER
→ declares entry and the object consulted

PARTICIPANT
→ contributes criticism, source, objection, experience or hypothesis

DERIVER
→ declares material adaptation, implementation, reuse or extension

CONTRIBUTOR
→ contribution produces an identifiable delta

FIXATION
→ accepted delta is documented through a commit
```

Transition between states is not automatic.

## 4. Current functional register

Until WEB4™ and dedicated interfaces replace this layer, GitHub serves as provisional infrastructure.

The functional mechanism is:

```text
STABLE PUBLIC LINK
→ «ENTRY / DERIVATION REGISTER» ISSUE FORM
→ PARTICIPANT GITHUB ACCOUNT
→ OBJECT CONSULTED
→ DECLARED PURPOSE
→ RELATION / DERIVATION IF ANY
→ POSSIBLE SPECIFIC SYNTHESIS ISSUE
→ DELTA
→ COMMIT
```

A GitHub account provides a minimum public identifier. A civil name is not required when unnecessary.

## 5. What it should record

The form should allow the participant to indicate:

- entry object: manifesto, IDEA, analysis, audit, protocol or general framework;
- source of contact: own search, received link, Innova_N email, third party or other;
- purpose: reading, research, criticism, implementation, translation, derivation, collaboration or follow-up;
- institution or project, optional;
- derivative-work URL, if any;
- need for attribution or genealogical link;
- privacy limits;
- consent for the record to remain publicly linked.

## 6. What it must NOT do

The Traceable Entry Register™ does not authorise:

- hidden fingerprinting;
- covert identity collection;
- publication of private emails;
- identity correlation without a legitimate basis;
- requiring ideological adherence in order to read;
- turning a visit into an automatic obligation to contribute;
- treating reading as appropriation.

Traceability begins when there is a recognisable act of entry, contribution or derivation.

## 7. Derivation and genealogy

The central concern is not that another person may learn from the framework. The material risk appears when a derived architecture erases provenance.

Therefore the following is proposed:

```text
ORIGIN
+ SHA / DATE
+ DERIVED OBJECT
+ DERIVING AUTHOR / TEAM
+ RETURN LINK
+ DELTA
= RECONSTRUCTABLE GENEALOGY
```

When the future licensing policy permits it legally, this ethical obligation of genealogy should also be translated into explicit attribution and reuse rules.

## 8. Relation to external contacts

Every new institutional communication should use a **living follow-up link**, rather than depending only on a specific figure or manifesto sent on a particular date.

The follow-up link should lead to:

- current framework state;
- latest manifesto;
- IDEA as the literary gateway;
- Traceable Entry Register™;
- Open Synthesis;
- deltas produced by external responses;
- public audits;
- versioned history.

Thus, a contact received in August 2026 can follow later evolution without requiring a new email for every change.

## 9. Herosion™

The working term **Herosion™**, still open to Synthesis, is introduced:

> inherited fractal harm that a system or generation receives from earlier layers, reproduces wholly or partly while operating upon them, and transmits again if no conscious repair occurs.

It does not imply automatic moral guilt for each generation.

It describes a functional chain:

```text
PREVIOUS HARM / DEBT
→ INHERITANCE
→ NORMALISATION
→ REPRODUCTION
→ NEW LAYER
→ AMPLIFIED OR TRANSFORMED INHERITED HARM
```

In software, a vulnerable dependency inherited through higher-level dependencies is a limited technical example of this pattern. In institutions, culture or knowledge, the analogy must be tested case by case and must not be used as automatic evidence of intention.

## 10. Security and openness

Tools such as dependency graph, Dependabot, secret scanning or code scanning do not constitute a surrender of the framework's canon. They are mechanisms for detecting technical debt and risk.

The correct safeguard is to separate:

```text
PUBLIC LAYER REQUIRED TO UNDERSTAND AND CONTRIBUTE
≠
COMPLETE INTERNAL IMPLEMENTATION
```

Not every operational mechanism must be published merely because the framework is open to criticism.

## 11. Future reserved manifestos

**Manifestos that still remain reserved are not named, described or reconstructed in advance in the public layer.**

The infrastructure is prepared so that, when there is an explicit decision to publish, any reserved manifesto may:

1. enter the canonical index;
2. receive an Open Synthesis Issue;
3. enter automatic navigation;
4. declare its genealogical relations;
5. link or redirect to previous nodes such as **IDEA** where appropriate.

Reservation does not equal non-existence; future publication does not authorise advance reconstruction of content.

## 12. MAXPROC ruling

The entry register is necessary **as a voluntary and traceable gateway for participation and derivation**, not as universal surveillance of the reader.

The recommended architecture is:

```text
PUBLIC READING
        ↓
FOLLOW THE FRAMEWORK
        ↓
REGISTER ENTRY (optional for mere reading; necessary for a recognisable relationship)
        ↓
CONTRIBUTE / CONTRADICT / IMPLEMENT / DERIVE
        ↓
SPECIFIC ISSUE
        ↓
DELTA
        ↓
COMMIT
        ↓
PUBLIC GENEALOGY
```

This solution preserves openness, privacy, authorship, precedence and return to source without claiming an identification capability that GitHub does not provide for anonymous readers.
